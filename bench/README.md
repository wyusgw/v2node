# v2node 多用戶 CPU / 記憶體基準測試（低→高配置，附 pprof）

本目錄是可重現的壓測工具，以及一次完整測量的結果（`results/`）。每次測量都附 pprof：`cpu.pprof`、`heap.pprof`，和用 `go tool pprof -top` 生成的 `cpu_top.txt`、`heap_top.txt`、`alloc_top.txt`。

## 怎麼測的

| 元件 | 作用 |
|---|---|
| `mockpanel/` | 模擬 v2board UniProxy API：下發節點配置和 N 個用戶，接收流量／在線上報 |
| `loadgen/` | 用 xray-core 自己的客戶端編碼（vless / vmess / trojan / shadowsocks）建立大量併發連線，每條連線隨機選一個用戶，按固定速率下載 32 KB/s、上傳 4 KB/s；平均 20 秒斷開，再換一個隨機用戶重連（持續產生握手） |
| `run.sh` | 用 `taskset` 把 v2node 綁到指定核數，放進記憶體 cgroup（超出就觸發 OOM），同時採樣 CPU 和 RSS，並抓 pprof |

- 機器：4 vCPU / 16 GB，Linux 6.18，Go 1.26.1，v2node `bbe2977` + xray-core `b6ee6fb`
- 節點：預設 ConnectionConfig（BufferSize 8 KB），TCP，無 TLS，sniffing 開啟（v2node 預設）
- 配置檔位（給 v2node 的資源）：**1C/512M → 1C/1G → 2C/2G → 3C/4G**；loadgen 和面板跑在剩下的核上
- 首包是 HTTP 請求行，sniffer 能立刻識別。無法識別的首包會讓 sniffer 等最多約 100 ms，會扭曲延遲數據。
- 目標位址 `11.11.11.11` 由 iptables DNAT 轉到本機 sink，因為 xray freedom 預設拒絕私有位址

重跑：`sudo bench/run.sh`（完整約 45 分鐘），或者縮小範圍：`PROTOCOLS=vless TIERS="1:512" LOADS=500 bench/run.sh`

## 結果一：用戶數對記憶體的影響（無流量，1C/512M）

`rss_anon` 是去掉映射的二進位檔（約 50 MB 的共享頁）之後的 RSS，比較接近真實的記憶體佔用。

| 協議 | 1k 用戶 | 10k | 50k | 100k | 每增加 1 個用戶 (anon) | 啟動時間 @100k |
|---|---|---|---|---|---|---|
| vless | 8 MB | 25 MB | 85 MB | 168 MB | ≈ 1.6 KB | 0.6 s |
| vmess | 10 MB | 32 MB | 121 MB | 240 MB | ≈ 2.3 KB | 0.6 s |
| trojan | 11 MB | 29 MB | 117 MB | 275 MB | ≈ 2.7 KB | 0.6 s |
| shadowsocks | 8 MB | 18 MB | 64 MB | 121 MB | ≈ 1.1 KB | 0.7 s |

所有協議空載 CPU 都是 0%，goroutine 數固定（12–15），不隨用戶數增長。10 萬用戶在 512 MB 上都能跑。

每個用戶的記憶體主要花在哪裡（`results/idle/*/u100000/heap_top.txt`）：
- 用戶的 email tag 字串 `fmt.Sprintf("%s|%s")`：100k 用戶約 23–27 MB
- `limiter.AddLimiter`：每個用戶的限速資訊，約 10–12 MB
- 各協議自己的驗證表：vmess 每個用戶一個 AES cipher（`aes.New` 38 MB）；trojan 保存 sha224 的 hex 字串，外加 sync.Map 節點（約 50 MB）

## Shadowsocks 修復前後

修復在 xray-core 分支 `multi-user-cpu-ram-pprof-223ti6`（`proxy/shadowsocks`），v2node 的 `go.mod` 已指向它：

1. **第一級快取改用客戶端 IP 做 key。** 原本用 `ip:port`，每個 TCP 連線的來源端口都不同，所以這層快取從來不會命中，每次握手都退回到第二級快取或全量掃描。
2. **已刪除的用戶可能繼續通過驗證（安全問題）。** `Del` 在每個分片只清掉第一個匹配的快取條目；另外，從快取命中的握手會把用戶重新寫回快取，但沒有確認用戶是否還存在，和 `Del` 並發時，已刪除的用戶會回到快取裡。現在會清掉所有條目，快取命中也會在讀鎖下確認用戶仍然存在。新增的測試在舊程式碼上會失敗。
3. **第二級快取原本不會過期。** 它最終會包含所有連過的用戶，等於全量掃描。現在條目 30 分鐘沒有成功握手就過期，並且最近成功的用戶先試。
4. **每嘗試一個候選用戶都要重建兩個 HMAC，另外分配 128 B 緩衝區（UDP 是 8 KB）。** 改成子密鑰派生不分配記憶體（與原本的 HKDF-SHA1 逐位元組一致，有測試驗證），緩衝區共用：全量掃描 1000 用戶從 1.35 ms、1.03 萬次分配降到 0.70 ms、1000 次分配。
5. 修掉兩處資料競爭（第二級條目原地改寫、第一級 `lastAccess` 在鎖外讀取），`go test -race` 通過。
6. **攻擊防禦維持關閉，和以前實際的狀態一樣。** 它的啟用條件依賴那個帶端口的 key，所以過去從未真正啟用過。如果 key 修好而不處理這一點，中轉 IP 會在第 6 個用戶時先觸發「啟用防禦」，第 7 個用戶時才被判定為中轉，這樣中轉 IP 可能被整個封禁，導致全節點斷線。

v2node 另外會在有 cgroup 記憶體上限（systemd `MemoryMax`、docker `--memory`）時，自動把 Go 的軟記憶體上限設為上限的 90%（已設定 `GOMEMLIMIT` 的話以它為準）。沒有這個設定時，GC 會讓 heap 長到存活資料的 2 倍才回收；CPU 跑滿、GC 跟不上時就會被 OOM kill。

測試條件：10,000 用戶，每條連線 32 KB/s，平均 20 秒重連，用三種客戶端模式對比（loadgen 參數見括號）：
- **直連**（`-sticky -src-ips`）：每個用戶固定帳號、有自己的 IP，最接近一般用戶直連節點
- **中轉後**（`-sticky`）：所有連線來自同一個 IP，像節點前面有中轉
- **最壞情況**（預設）：每次重連都換一個隨機用戶，而且來自同一個 IP，完全沒有局部性

格式：CPU% · 實際下行 Mbps · TTFB p50/p99（只統計預熱之後建立的連線）。

| 模式 | 檔位 / 連線 | 修復前 | 修復後 |
|---|---|---|---|
| 直連 | 1C/512M · 500 | 42% · 131 · 2.6/62 ms | 35% · 131 · **0.9/8.7 ms** |
| 直連 | 1C/512M · 2000 | 98% · **227**/524 · 3976/10310 ms · 8512 次錯誤 | 98% · **452**/524 · 491/5178 ms · 1709 次錯誤 |
| 直連 | 2C/2G · 500 | 49% · 131 · 1.9/25 ms | 45% · 131 · 0.7/4.7 ms |
| 直連 | 2C/2G · 2000 | 180% · 466/524 · 183/6755 ms · 971 次錯誤 | **139%** · **526**/524 · **10/446 ms** · 0 錯誤 |
| 中轉後 | 1C/512M · 500 | 43% · 131 · 2.8/63 ms | 39% · 131 · 2.1/39 ms |
| 中轉後 | 1C/512M · 2000 | ❌ **OOM** | 98% · 404/524 · 2678/5794 ms |
| 中轉後 | 2C/2G · 500 | 49% · 131 · 1.9/30 ms | 48% · 131 · 1.6/22 ms |
| 中轉後 | 2C/2G · 2000 | 183% · 467/524 · 196/4933 ms · 535 次錯誤 | 160% · **523**/524 · 37/667 ms · 0 錯誤 |
| 最壞情況 | 1C/512M · 500 | 96% · 127 · 679/1805 ms | **67%** · 131 · 49/193 ms |
| 最壞情況 | 1C/512M · 2000 | 99% · 117/524 | 99% · 200/524 |
| 最壞情況 | 2C/2G · 500 | 112% · 131 · 40/158 ms | 75% · 131 · 11/47 ms |
| 最壞情況 | 2C/2G · 2000 | 195% · 215/524 | 196% · 425/524 |

- 2C/2G、2000 連線時，查找用戶佔的 CPU：中轉後從 37% 降到 16%（同時多處理了 12% 流量）；直連則已經不在前 40 個熱點裡。
- 1C/512M、2000 連線對 SS 來說已超出單核能力（任何模式 CPU 都是 98–99%）。修復後不再被 OOM kill（峰值 445–449 MB），吞吐量是修復前的 1.7–2 倍。中轉後這一列的改善，有一部分來自上面的軟記憶體上限。
- 中轉後的節點每次握手仍然要逐個試最近在線的用戶，這是 SS 多用戶 AEAD 協議本身沒有用戶標識造成的。修復降低了每次嘗試的成本，但沒辦法改變這個 O(在線用戶數) 的本質。如果中轉支援 PROXY protocol，節點就能拿到真實客戶端 IP，走直連那條路。

資料：`results-ss/{old,new}/{legacy,relay,direct}/`，每次執行都有 cpu/heap pprof。

## 配置建議（10k 用戶，連線平均 32 KB/s）

| 檔位 | vless / trojan | vmess | shadowsocks（多用戶 AEAD，修復後） |
|---|---|---|---|
| 1C/512M | ≤ 2000 連線（約 500 Mbps） | ≤ 1500 連線 | 約 1000 連線（500 連線時 CPU 35–39%） |
| 1C/1G | 同上；多出來的記憶體只能避免 trojan 過載時 OOM | 同上 | 同上 |
| 2C/2G | 約 5000 連線 / 1.3 Gbps | ≤ 3000 連線 | 約 2500 連線（2000 連線時 CPU 139–160%，跑滿 524 Mbps） |
| 3C/4G | > 5000 連線（推算） | 約 5000 連線（推算） | 約 4000 連線（推算） |

粗略換算：每 100 Mbps 大約需要 vless 15%、trojan 16%、vmess 25–29% 的單核 CPU。每條活躍連線大約佔 75–110 KB 記憶體。

## pprof 看出的熱點與優化方向

1. **Shadowsocks 多用戶握手曾是最大的瓶頸（已修復，見「Shadowsocks 修復前後」）。** 修復前，只有 25 次握手/秒時 `Validator.GetWithCache` 就佔了 47% 的 CPU（`results/load/shadowsocks/1c512m/c500/cpu_top.txt`）。原因是快取 key 帶端口所以從不命中，每個新連線都要拿大量用戶的密鑰試一遍 HKDF-SHA1 + AEAD。用戶很多、又在中轉後面的節點，建議改用 SS2022（`server_key`，按 EIH 直接查用戶），或者 vless / trojan。
2. **VMess 的 `AuthIDDecoderHolder.Match` 佔 22% CPU**（2C、5000 連線）。每次握手都要用 AES 逐個試用戶，而且每個用戶常駐一個 AES cipher。這是 vmess 協議本身的代價，所以同樣配置下 vmess 能承載的連線數比 vless 少。
3. **CPU 飽和時記憶體會失控。** vmess 在 1 核上遇到 5000 連線，連 1 GB 都 OOM：不是洩漏，是 GC 跟不上、處理不過來的連線持續堆積。v2node 現在會依 cgroup 上限自動設 Go 軟記憶體上限（見上文），在 SS 測試中消除了 OOM。沒有 cgroup 上限的 VPS 可以手動設 `GOMEMLIMIT`（例如記憶體的 80%）。vmess / trojan 那幾列是加入這項之前測的。
4. **負載下的記憶體主要是連線緩衝區：** `bytespool` 在 5000 連線時佔 96–109 MB heap，每條連線大約 3 個 goroutine（加上 vmess 的 cipher，約 6 個）。BufferSize 已經是 8 KB，再調小的收益有限。
5. **vless / trojan 的 CPU 大約 65% 花在系統調用**（每條連線每 100 ms 只收發幾 KB 的小包），用戶態本身已經很輕。
6. 空載時每個用戶的記憶體中，email tag 字串、limiter 和 sync.Map 佔大頭（見結果一），10 萬用戶合計約 30–50 MB，可以進一步壓縮，但優先級低。

## 目錄結構

```
results/
  idle.csv, load.csv
  idle/<協議>/u<用戶數>/         heap.pprof, heap_top.txt, alloc_top.txt, node.log
  load/<協議>/<核>c<MB>m/c<連線>/ cpu.pprof, heap.pprof, *_top.txt, loadgen.json, node.log
```

pprof 檔本身帶有符號，可以直接打開，例如：
`go tool pprof -http=:8080 results/load/vmess/2c2048m/c5000/cpu.pprof`
